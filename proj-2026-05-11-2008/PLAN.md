# Plan: Nemotron Pipecat Assistant Aggregator Alignment

Project directory: `./proj-2026-05-11-2008`

## Context

`NemotronOmniAudioLLMService` runs an internal multi-pass tool loop, fabricates assistant/tool rows locally, and rejects the tool-followup contexts Pipecat normally sends back upstream. This causes drift between the service's private execution path and the shared `LLMContext` that the assistant aggregator owns — the root cause of the "tool history missing from context" symptoms identified in the May 11 eval review. The planning step traced the drift to a deeper design flaw: the vLLM conversation cache uses a **server-authored assistant ledger** (the server appends generated assistant/tool rows to `committed_messages` and re-synthesizes them on cached followups), which is fundamentally incompatible with a client whose shared `LLMContext` is the real transcript. So this project deliberately replaces that protocol with a **client-authoritative `committed_messages`** model plus a **prompt-authoritative engine checkpoint**. This supersedes the server-authored-ledger / `tool`-only-suffix model in `proj-nemotron-pipecat-assistant-aggregator-alignment.md` §5.5 (`proj-nemotron-pipecat-assistant-aggregator-alignment.md:442`); that supersession is intentional and in scope — we own the vLLM fork.

The fix, end to end:

- one inference per upstream `LLMContextFrame`, with inference backgrounded so superseded turns can be cancelled promptly while audio/control frames keep flowing
- sync tool execution routed through Pipecat function-call frames (`FunctionCallsStartedFrame` / `FunctionCallInProgressFrame` / `FunctionCallResultFrame` / `FunctionCallCancelFrame`) with a Nemotron-owned **serial** dispatch policy layered on `LLMService`'s sequential runner — the internal multi-pass tool loop is deleted
- bash tool results exposed to the model as structured JSON with a fixed field set, never legacy tagged text
- a `NemotronAssistantAggregator` that, **only on sync-tool / mixed text+tool passes**, materializes the exact provider-visible `assistant(tool_calls)` row and its `tool` rows in the live shared `LLMContext` as provisional pass-owned rows — cleared on supersession, carried forward verbatim into the next projected request otherwise — and **delegates to stock `LLMAssistantAggregator` for everything else** (text-only passes, marker/thought handling, summarizer, turn lifecycle, interruption of plain-text turns)
- conversation-cache logic rebuilt as a pure request **projection** over the normalized shared-context transcript relative to a client-acknowledged prefix, with a `cache_shape_fingerprint` guard; vLLM stops authoring an assistant ledger and instead stores `committed_messages` = "what the client sent" plus an engine checkpoint = `render(committed_messages, gen_prompt=False)`
- developer-role handling aligned now with `BaseOpenAILLMService` at the OpenAI-adapter boundary (`developer → user`), not the local `developer → system` rewrite

Reference design: `proj-nemotron-pipecat-assistant-aggregator-alignment.md`. Adversarial-review notes that shaped this revision: `ISSUE_INVESTIGATION.md` and the review at `/tmp/plan-review/proj-2026-05-11-2008-PLAN-adversarial-review.md`.

### Step ordering and one non-deployable window

Steps run in order; each is independently implementable and testable **except** that **steps 5 and 6 are a coupled pair**: step 5 makes the *service* speak the new client-authoritative wire protocol while the *server* still speaks the old one, so the bot is **not end-to-end functional between step 5's commit and step 6's commit**. Step 5 ships with client-side unit tests; the end-to-end regression check (`scripts/run_mixed_rtvi_regression.py`) is part of step 6's verification. Every other step leaves the bot runnable.

`tests/test_nemotron_omni_aligned.py` is grown incrementally — each step adds the tests for the behavior it introduces (listed in that step's verification). Step 8 only consolidates: it organizes the file into the three named layers, audits coverage against steps 1–7, and finalizes the disposition of the legacy test files.

- [x] **3. Replace the internal tool loop with Pipecat function-call re-entry and a Nemotron-owned serial dispatch policy**

  Delete the internal multi-pass loop. Tool calls now flow through Pipecat's function-call frames; the LLM re-enters via an `LLMContextFrame` pushed back upstream by the assistant aggregator. The stock `LLMAssistantAggregator` still owns the context writes in this step (synthesized per-tool-call `assistant`/`tool` rows, then `_update_function_call_result` on the result) — exact-row ownership is step 4.

  **Conversation caching is fully disabled in steps 3–4.** The old `_payload_after_tool_calls` / `_conversation_payload_messages` projection was built around the internal loop's row shapes and cannot be reconciled with the stock aggregator's rows or with the new wire protocol; rather than carry a zombie, delete it here. Every request sends the **full normalized history**, and the service **stops sending `conversation_id`** entirely (and the bot stops constructing/passing it for now). Do **not** instead send `conversation_id` with `conversation_require_cache` omitted: the current vLLM still acquires a lease and *opportunistically* attaches its (server-authored-ledger) checkpoint whenever the request's leading rows happen to match `committed_messages`, regardless of `conversation_require_cache` (`vllm-v0.20.0/.../serving.py:594,651,784`) — that would entangle steps 3–4 with the very ledger semantics we're replacing, and the client's stock-aggregator assistant rows may or may not byte-match the server's generated ones, so the behavior would be a confusing mix of opportunistic attach and silent rebase. Dropping `conversation_id` makes every request a true one-off — zero interaction with the old ledger. Step 5 reintroduces `conversation_id` and the cache logic from scratch under the client-authoritative contract. This is the only window where the bot runs without prefix reuse — correctness preserved, performance not. (If `scripts/run_mixed_rtvi_regression.py` has a hard cache-hit-rate assertion, relax it for steps 3–4 and re-tighten in step 6.)

  In `src/nemotron_voice/services/nvidia/nemotron_omni.py`:
  - Pass `run_in_parallel=False` to `LLMService.__init__`, and **do not** depend on grouped-parallel execution. This makes `LLMService.start()` / `stop()` / `cancel()` create and tear down `_sequential_runner_task` automatically (the service already overrides `start`/`stop`/`cancel` and calls `super()` — keep that).
  - Loose ends to clean up here: the `suffix_only_conversation` constructor param / `_suffix_only_conversation` flag becomes meaningless (under the new contract suffix-when-possible is *the* behavior, not an opt-in mode) — remove it now and stop the bot from passing `NEMOTRON_OMNI_SUFFIX_ONLY_CONVERSATION`. The `conversation_id` plumbing (the constructor param, `self._conversation_id`, the bot's `NEMOTRON_OMNI_CONVERSATION_ID` / `NEMOTRON_OMNI_ENABLE_CONVERSATION_CACHE` wiring) is *also* removed here (caching is fully disabled) and **reintroduced fresh in step 5** along with the rest of the cache logic; do not leave it dangling.
  - In `_process_context`, after collecting tool-call deltas exactly once per streamed response, build `FunctionCallFromLLM` items (each carrying the **live** shared `context`, not the snapshot — see the live-context contract below) and call `await self.run_function_calls(function_calls)`. Then `_process_context` **returns**. Do **not** re-enter an internal tool loop, and do **not** await the tool batch or build the followup request here.
  - **Generation-task / tool-batch / frame-ordering — the real invariants (don't overclaim).** `run_function_calls()` in `run_in_parallel=False` mode only *enqueues* runner items into `_sequential_runner_queue` and returns; the long-lived `_sequential_runner_task` executes them one at a time, and tool lifecycle frames (`FunctionCallInProgressFrame`, `FunctionCallResultFrame`) are broadcast from *that* task. So it is **not** true that the generation task finishes before any tool handler runs — once `_process_context` returns and the wrapper's `finally` awaits `push_frame(LLMFullResponseEndFrame())`, the event loop can hand control to `_sequential_runner_task`, which may broadcast `FunctionCallInProgressFrame` before or after `LLMFullResponseEndFrame` is pushed. What *is* guaranteed, and what the design relies on:
    - the service pushes the `NemotronExactAssistantMessageFrame` (step 4) and then — inside `await run_function_calls(...)` — broadcasts `FunctionCallsStartedFrame`, **both before `_process_context` returns**, hence both before the wrapper pushes `LLMFullResponseEndFrame`. Frames flow through each processor's FIFO in push order, so the `NemotronAssistantAggregator` sees `NemotronExactAssistantMessageFrame` → `FunctionCallsStartedFrame` → `LLMFullResponseEndFrame` in that order. It therefore *knows it is a sync-tool pass* (via the exact-message frame and `has_function_calls_in_progress`, both established by `FunctionCallsStartedFrame`) by the time it handles `LLMFullResponseEndFrame` — which is the only ordering step 4's mixed-pass text-suppression needs (it keys the suppression off that state, not off whether a handler has run). The relative timing of `FunctionCallInProgressFrame` vs `LLMFullResponseEndFrame` is immaterial.
    - the followup `LLMContextFrame` is pushed by the aggregator only after the *final* tool result (plus the aggregator's bot-speaking/queued-result deferral checks) — many pipeline hops after `_process_context` returned — so the originating generation task is long done by then; the "cancel any prior generation task on a new `LLMContextFrame`" rule is a no-op against a finished task for ordinary tool re-entry. Supersession of an *in-flight tool batch* (a newer user turn / `InterruptionFrame`) is handled by running-task cancellation + queued-stale-item invalidation (below), not by generation-task cancellation.
    - cancelling the generation task mid-`finally` still runs the `finally`, so `LLMFullResponseEndFrame` is still emitted under supersession — `test_response_lifecycle_frames_pair_under_supersession` (extended here for the tool-batch case).
  - **Live `FunctionCallParams.context` contract** (this is real Pipecat behavior — see `ISSUE_INVESTIGATION.md` §1): keep the same live `context` object in `FunctionCallFromLLM.context` / `FunctionCallParams.context`; handlers may read and mutate it; the followup request after the serial batch completes is built from the then-current live shared context **after** those handler mutations (step 5 builds it; in this step the stock aggregator's `push_context_frame(UPSTREAM)` does), never from the original snapshot plus a private staged ledger.

  Implement a service-owned **serial** tool-dispatch policy by reusing Pipecat core runner pieces — prefer the narrowest override seam:
  - Reuse `LLMService.run_function_calls()` shape: keep the `on_function_calls_started` event and `FunctionCallsStartedFrame` broadcast for the full batch; reuse `FunctionCallRunnerItem`, `_run_function_call()`, `FunctionCallParams` / `result_callback` wiring, registry lookup, and timeout handling. Avoid reimplementing `run_function_calls()` unless there is genuinely no other way.
  - **The single-followup guarantee comes from explicit per-runner `run_llm` flags, not from sibling-group inference.** Override `_run_sequential_function_calls()` to set `runner_item.run_llm = False` for the first `N-1` items and `True` for the final item, then delegate to the parent queueing path. In `LLMAssistantAggregator._handle_function_call_result`, `frame.run_llm` (set from `runner_item.run_llm`) is checked *before* the `group_id` branch, so this overrides the grouped-completion logic. (Setting `group_parallel_tools=False` is harmless but not required; do not rely on `group_id` to delay re-entry. Stated as the contract: only the last serial result sets `run_llm=True`.)
